# Règles pour les Agents Vibe - Projet NextCloudDreamAndroidTv

## 📋 Règles Générales

### 1. **Commits Atomiques**
Chaque commit doit représenter **une seule fonctionnalité ou correction** logiquement cohérente.
- ✅ **BON** : "Add standalone video playback support"
- ❌ **MAUVAIS** : "Add video support and fix memory leak" (deux choses différentes)

### 2. **Tests avec le Code**
**TOUJOURS** commiter les tests unitaires **dans le même commit** que le code qu'ils testent.

**Pourquoi ?**
- Maintenir la cohérence entre code et tests
- Faciliter les reviews (le reviewer voit code + tests ensemble)
- Éviter les commits "orphelins" de tests
- Permettre les bisects git efficaces

**Exemples :**
```bash
# ✅ BON : Code et tests dans le même commit
git add app/src/main/java/.../VideoStream.kt \
         app/src/test/java/.../VideoStreamTest.kt
git commit -m "Add VideoStream with tests"

# ❌ MAUVAIS : Code et tests séparés
git commit -m "Add VideoStream"          # Code seulement
git commit -m "Add VideoStream tests"     # Tests seulement
```

### 3. **Structure des Commits**

#### Format du message de commit
```
<Type>(<scope>): <description>

<corps détaillé>

- Point 1
- Point 2

Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>
```

#### Types de commits
- `feat`: Nouvelle fonctionnalité
- `fix`: Correction de bug
- `docs`: Documentation
- `style`: Formatage, missing semicolons, etc.
- `refactor`: Refactoring de code
- `perf`: Amélioration de performance
- `test`: Ajout de tests (seulement si le code était déjà commité - à éviter)
- `chore`: Changements de build, dépendances, etc.

### 4. **Signatures des Commits**
Toujours signer les commits avec :
```
Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>
```

### 5. **Vérification avant Commit**
Avant de commiter, toujours vérifier :
- [ ] Le code compile (`./gradlew :app:compileDebugSources`)
- [ ] Les tests passent (`./gradlew testDebugUnitTest`)
- [ ] Pas de fichiers non voulus (`git status`)
- [ ] Le message de commit est clair et descriptif
- [ ] Les tests sont inclus dans le commit (si applicable)

### 6. **Gestion des Branches**
- `main`: Branche principale, toujours stable
- `feature/*`: Branches de fonctionnalité
- `fix/*`: Branches de correction
- `release/*`: Branches de release

### 7. **Nommage des Fichiers de Test**
Les fichiers de test doivent suivre la convention :
```
<NomDeLaClasse>Test.kt    # Pour les tests unitaires
<NomDeLaClasse>InstrumentedTest.kt  # Pour les tests instrumentés
```

Et être placés dans :
```
app/src/test/java/...    # Tests unitaires JVM
app/src/androidTest/java/...  # Tests instrumentés Android
```

### 8. **Couverture de Test Minimale**
- Logique métier pure (sans dépendances Android) : **100%** de couverture visée
- Composants avec dépendances Android : Tests instrumentés recommandés
- Code UI : Tests manuels acceptables, tests Espresso idéaux

### 9. **Utilisation des Coroutines**
- Toujours utiliser `Dispatchers.IO` pour les opérations bloquantes (réseau, disque)
- Toujours utiliser `Dispatchers.Default` pour les opérations CPU-intensive
- Toujours utiliser `Dispatchers.Main` ou `Dispatchers.Main.immediate` pour les mises à jour UI
- Toujours utiliser `runCatching` ou `try-catch` pour gérer les exceptions dans les coroutines

### 10. **Gestion des Ressources**
- Toujours libérer les ressources dans des blocs `finally` ou `use`
- MediaPlayer: `player.release()` dans `finally`
- Surface: `surface.release()`
- Bitmaps: `bitmap.recycle()` quand plus besoin
- Files: Utiliser `use` ou `close()`

## 🎯 Checklist avant PR

- [ ] Code compile sans erreurs
- [ ] Tous les tests unitaires passent
- [ ] Pas de warnings de lint
- [ ] Documentation mise à jour (README, CLAUDE.md)
- [ ] Messages de commit clairs et atomiques
- [ ] Tests inclus dans les mêmes commits que le code
- [ ] Pas de memory leaks (vérifier onDestroy, close, release)
- [ ] Gestion des erreurs robuste
- [ ] Code suit les conventions du projet

## 🧪 Tester sur l'émulateur

**Lire `docs/TESTING_GUIDE.md` avant tout test sur émulateur.** Une seule commande monte
tout (faux serveur Nextcloud, configuration de l'application, économiseur lancé) :

```bash
tools/fake-nextcloud/run_emulator_test.sh
```

- Ne jamais utiliser `python3 -m http.server` ni `http://10.0.2.2` : la synchro échoue.
- Ne jamais autoriser le HTTP en clair dans `app/src/main/` (release) : seulement dans `app/src/debug/`.
- Une fonctionnalité n'est « vérifiée » qu'avec des preuves : ligne logcat, requête dans
  `server.log` et capture d'écran. Dire aussi ce qui n'a pas été testé.
